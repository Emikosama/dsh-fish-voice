# 延迟基线与验收边界

## 2026-11-17 · 10 万 token 开麦预热门槛

0.5.39-rc.5 开始，鱼应在当前语音 Agent 可渲染后重新估算可用于预热的输入。超过 100,000 才准备预热请求。等于或低于门槛会记录 `skipped-short-input`，并直接跳过。计算使用待发送的系统提示词、可用历史、工具声明，排除本地会话元数据和不会投递的附件。准备完毕后再核对适配器投影，覆盖适配器或历史变化。提供商自动缓存保持原样。

该门槛是本地估算。英语部分按此前 DeepSeek-V4.1-Flash 长上下文约 4.7 字符/token 的实测比值，汉字部分按 DeepSeek 的 0.6 token/字符近似。实际分词会因模型和内容变化。本地判断免去额外计数请求或分词模型下载。 [DeepSeek token 用量说明](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)

## 2026-11-17 · 语音首音与快档

使用原版 rc.3 和新版并行预合成方案，在 Windows 上调用真实 Edge「晓伊」，用 DSH 附带的运行时和 VB-Audio 回环。用同文按旧版、新版、新版、旧版顺序各两次，计时从发起朗读到回环首音。

| 样句 | rc.3 首音中位数 | 并行预合成首音中位数 |
| --- | ---: | ---: |
| 普通话单句 | 3.87 秒 | 3.23 秒 |
| 普通话多句 | 3.99 秒 | 3.33 秒 |

每条回复的句段共用一个播放器，最多同时合成两段。先串行合成下一段的试做水位有 1.59–2.40 秒的最长静音间隔。并行版多句最长间隔约 1.05 秒，原版约 0.70 秒，单句间隔均约 0.27 秒。间隔按回环振幅阈值统计，也包括朗读本身的停顿。对照走虚拟音频设备，测试账号与公网波动会影响首次等待。注入首段网络错误后返回文字模式，回环未捕获到声音。

鱼应自己的固定角色提示词和偏好包从约 7,600 字符缩到约 2,300 字符。固定规则进入系统提示一次，自定义偏好仍由宿主排在工作区 AGENTS 后。这是项目自有文字的长度，不是整个请求或供应商的 token 数。

完整短答使用 `whale_voice_speak` 的 `final: true`。宿主确认该步只有这次朗读，且朗读或文字兜底成功后直接结束回合。还要派工或继续工具的回应按原流程执行。Windows 隔离宿主的原生工具回归验证了短答只发出一次带语音工具的模型请求。

已用 Windows DSH rc.3 实际 DeepSeek Messages 适配器及回环测试服务器抓取请求。快档的预热和首轮正文都发出 `thinking.type: disabled`，使用相同的系统提示和五个工具。正式无声明模型的离线测试使用真实适配器包和没有目录项的测试模型。这里测的是实际序列化和宿主回合控制。提供商是否接受和发出推理内容，需实测对应的远端路线。

这次回环检查发现旧版新会话传入空工具历史时，DeepSeek 适配器会丢掉整组工具。新版只有已保存工具头与当前工具匹配时才复用其折叠历史，否则提交当前工具。

## 2026-11-17 · 开麦时预热对话模型

手动开麦成功后，鱼应在后台从当前语音 Agent 读取已渲染的系统提示词、可复用的历史前缀和工具声明，以同一模型与思考档位发起一次有输出上限的请求。服务端需要有效输入时使用一个请求内的占位符。预热不写入 Agent 对话、不执行工具，收到首个有效输出即取消。收到真实输入、关麦或切会话时也会取消，正常语音回复不等待预热。缺少所需接口的宿主照常开麦。

缓存只可能命中与下一轮请求一致且已经在服务端写入的前缀。真实转写和宿主随轮次追加的上下文在开麦时尚不可知。额外请求可能计费。客户端停止接收时的服务端缓存写入和计费由供应商决定。参见 [DeepSeek 上下文缓存](https://api-docs.deepseek.com/guides/kv_cache/)。

`llm_cache_warmup` 记录预热结果与收到首个输出的时间。`llm_timing` 以 `traceId` 与转写计时配对，并记录真实请求首个模型增量及宿主有回报时的 `inputTokens`、`cacheReadTokens`、`cacheWriteTokens`。验收时使用相同路线、工具、长提示词和配对的开麦后等待时间，对比有无预热的真实首轮请求缓存命中、首个模型增量及回环首音 P50/P95。预热请求发出或收到首个输出只证明预热路径运行。

其他优化先看分段结果。提示词和工具的大段固定内容优先稳定字序并去重。本轮检查发现鱼应的规则同时写进系统提示和运行上下文。开麦后首句快慢还可受模型思考档位影响。朗读侧可复用播放器进程，或在第一个完整短句到达时开始流式合成和播放。ASR 暖机旧基线已在几十到百余毫秒量级，优先查清模型与朗读耗时。

## 2026-11-11 · 本地计算

测量日期：2026-11-11。Windows 测试机 上导入原 Python 帮工（不调用 main），使用确定性 16kHz 正弦合成信号，不录音、不播放、不调用 embedding HTTP、不向真实 DSH 会话投递。以下仅测本地计算，不是语音准确率或完整对话体验。

| 阶段 | 3 秒合成信号，暖机 | 10 秒合成信号，暖机 |
|---|---:|---:|
| SenseVoice ASR | 45.7–48.9ms | 124.8–138.7ms |
| CAM++ 声纹提取 | 17.6–18.6ms | 101.5–106.0ms |
| 韵律 | 2.7–3.0ms | 6.2–6.9ms |

冷模型加载：SenseVoice 802ms；CAM++ 266ms。首次韵律导入及 3 秒计算合计 135ms。不能用正弦信号识别结果证明真实中文、噪声或多人环境中的准确率。

当前侧键 PTT 松开即结束录音，30ms 轮询。手动自动收段的 1200ms 和常听的 600ms 是不同模式的静音参数，不应把 1200ms 算到每次侧键松开后的等待里。

本机输出是显式 speak 工具，自动全文朗读关闭。speak 默认 wait=false，在完整工具参数到达后排队；TTS 本身从原生 /tts 读取流，收到第一块 PCM 即开始播放。原生模型 60 秒空闲后卸载。2026-11-08 旧 README 记录的冷首播 3.683 秒、热首播 0.664 秒属于历史数据，未在本轮重新测量。自动全文朗读中的 320 字缓冲并不作用于当前显式 speak 模式。

## 2026-11-15 · Windows 桌面 0.2.2-rc.3

使用独立桌面 profile、VB-Audio 虚拟声卡、合成中文短句和本机 SAPI，实测 `d644b58` 与 0.5.38。两版交替运行，各四次。计时从发起朗读到回环首次超过采样阈值，含进程开销。

|  Windows 系统朗读 | 首音中位数 |
|---|---:|
| 独立进程先枚举音色，再启动合成和播放 | 1,201 ms |
| 合成进程直接选择音色、合成和播放 | 795 ms |

不存在的显式音色返回 `TTS_SYSTEM_VOICE_MISSING`，回环未检测到播放。完整诊断仍能独立读取能力。

桌面使用本地 SenseVoice、真实 WinMM 输入和 Windows 系统朗读，Agent 模型由离线脚本固定输出工具调用。三次按住说话入口的停止请求至回环首音为 1,038–1,175 ms，帮工收段至转写为 57–61 ms。另在唤醒模式验证一条普通背景语音被丢弃，一条“小鲸鱼，请确认识别正常”进入会话。结果不包含远端模型首 token、物理麦克风和扬声器声学路径，也不推断噪声下的唤醒率。

本轮优先缩短已测到的系统朗读等待。保留独立语音会话、常驻识别和授权边界。若后续自由麦的主要延迟在静音收段，可对比 [dsh-voice-mode 的 Zipformer 流式识别](https://github.com/qishuilalala/dsh-voice-mode) 与 [LiveKit 的端点和回合检测](https://docs.livekit.io/agents/logic/turns/tuning/)，先用同一批中文停顿和噪声样本测误截断、误唤醒及首音。预生成还需要在最终收段前发送上下文，作为授权行为单独评估。
