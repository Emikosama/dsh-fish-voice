# 鱼应问题复核与修复边界（2026-11-11）

本次核对私有仓库 issues #3、#4、#5，并以开发分支 `bddbcd055b1c1d488aa7efd68273784444056a9c` 的 0.5.5 源码为基线。问题描述中的 Windows 现场来自 0.5.4；云端源码复现不替代新版本的 Windows 桌面、麦克风、扬声器或真实模型验收。

## #3：任务超时与请求隔离

已复现旧 `_spawn` 的任务成功后仍产生超时事件并释放全局录音器。Node 侧原有错误处理按 pending 插入顺序拒绝首个请求，错误没有可靠归属。只补 `timer.cancel()` 不足以处理线程启动、完成和超时回调之间的竞争，也不能防止真实超时或迟到结果影响另一项请求。

修复验收必须包含：瞬时完成、异常完成、真实超时、完成与超时竞争、迟到结果、并行请求，以及旧任务超时不影响新的录音。超时不等于 Python 推理线程已被强制终止，不能据此声称底层计算已经停止。

## #5：三档思考不能越过宿主能力检查

已核对并直接测试官方发布 `@deepseek-ai/dsh-llm@0.2.2-rc.1`：模型未公布某个 reasoning effort 时，显式请求该档会在 provider I/O 前报 `UNSUPPORTED_REASONING_EFFORT`。因此，“未公布 off 也直接写入，可能无效但能发出”不符合当前宿主契约。放开插件的 high 校验也不等于提供商已经支持 high。

基础契约区分两种选择：

- 明确选择快速／均衡／高性能时，分别严格请求 off／low／high。无法确认对应能力就清楚报告不可用，不伪造能力声明、不暗换档位。
- 原有配置保留兼容策略：使用可用的公布默认值或提供商默认，并清楚记录请求、实际选择和回退原因。旧配置不会自动迁移成严格快速模式，避免使现有可用路由突然失效。

宿主接受、请求实际发出、服务端是否遵守是不同事实。能力表中的 off 不证明服务端真的关闭思考；同样，十几秒响应不能独自证明延迟由思考造成。真实测量须分开记录收段、ASR、请求排队、模型首次输出、TTS 加载、合成和实际首声。

当前关闭语音会清理该语音根的后台任务树。不能用“关闭再开启”实现切档，却对用户承诺后台任务不受影响。本批仅提供在完全停用状态保存档位的基础能力，不自动关闭、不自动重开、不启动麦克风或任务。运行中无损切档需另行实现并验证生命周期。

### TTS 常驻尚未完成

外部 `dsh-dstuber`／`dsh-speak` 的当前源码与驻留接口尚未核实，本批不伪造 pin/lease API，也不声称快速模式已经让 TTS 常驻或预热。相关能力必须独立标示为尚未支持／未核验。

后续应先核实带归属的驻留租约、预热、释放与崩溃回收，再做实际接入。单次 speak 的 keepAlive 标记不能替代整个语音授权的生命周期管理。验证常驻时，两句间隔必须超过原有 60 秒卸载阈值，同时观察实际模型加载次数与首声时间；短间隔连续两句本来就可能命中旧缓存。

## #4：先设计，再修改实际浮条

现有源码将浮条 `Controls` 与独立插件设置页 `Settings` 分开。模型路径、音频配置和历史已在设置页，不应按 issue 的混合描述盲目迁移一遍。

本批不改视觉结构。一级界面应聚焦高频操作、实际麦克风状态和必要异常处理；低频配置放入次级界面。需先完成视觉稿，再实现相应交互、动效、键盘操作与窄窗验证。“语音权限已开启”不等于“正在录音”，不能以美化为由混淆状态。

## 0.5.6 的具体改动

- 帮工启动声明 `requestProtocol: "whale-request/1"`，Node 对每条命令生成唯一 requestId，响应、错误和等待者按 ID 匹配。不支持此协议的旧 helper 会明确报错并停止重启，不回退到 FIFO。
- 已超时／已完成的带 ID 结果不再变成自由投递的语音输入；常听、侧键等主动事件仍走原有语音授权与代数检查。旧子进程的 stdout 继续被进程身份隔离。
- 看门狗在任务启动前建立，完成与超时共享终态锁；迟到事件被丢弃。文件分析不会释放麦克风，注册只清理自己持有的录音器，超时后迟到的声纹计算不能再写入注册结果。
- 档位选择写入 `voiceSession.performanceMode`。旧 `reasoningEffort`（含 null/缺省）保持兼容；不同配置层的高优先级选择覆盖低优先级别名，同一配置中的真实冲突仍报错。
- 后台提供模式能力查询和停用状态下的 revision 校验保存接口。设置保存、能力检查不会重建会话、调用模型或隐式停工；宿主能力查询不证明远端服务端遵守对应档位。

### 后续 UI 可使用的后台接口

- `inspectPerformanceModes(agent, signal)`：返回当前路由的公布档位、严格模式可用性、实际选择策略及 TTS 未核验状态。
- `setPerformanceMode({ revision, performanceMode }, agent, signal)`：只有完全停用且清理完成时才能保存，支持 fast/balanced/high/compatibility。保存不授予语音权限、不自动开启。
- `status().voiceSession.performance`：当前运行根的请求／选择／实际请求观察状态，与设置页的下一次偏好分开。`fullyStopped` 与 `ttsResidency` 单独提供。

以上接口尚未接入新的 UI 命令或控件；不能把后台契约存在说成三档界面已完成。运行中切档、TTS 租约、原创视觉实现和真实设备验收仍是后续工作。
